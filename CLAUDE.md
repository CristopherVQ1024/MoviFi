# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

MoviFi is a vehicle-management app (vehicles, maintenance schedules, expenses/budget, AI chat). The repo holds two independent projects; there is no root-level package.json or workspace tooling.

## Backend (`movifi-backend/`)

Single-file Express API in `server.js` (Spanish naming throughout: `vehiculos`, `mantenimientos`, `gastos`, `presupuesto`). Raw SQL via `pg` against PostgreSQL, no ORM. The schema and seed live in `schema.sql` (run it by hand against the DB); incremental changes for an already-created DB go in `migraciones/NNN-*.sql` and must also be folded into `schema.sql`.

- Run from `movifi-backend/`: `npm start` (or `npm run dev` for `--watch`). Env vars load from `movifi-backend/.env` via `node --env-file`; there is no `dotenv`. `.env` is git-ignored and there is no `.env.example`.
- Env vars: `PORT`, `JWT_SECRET`, `GOOGLE_CLIENT_ID`, `MISTRAL_API_KEY`, `MISTRAL_CHAT_MODEL` (model for `/chat`; this key has a 0 req/min quota on `mistral-small`/`mistral-medium` chat completions, so `.env` sets `ministral-8b-latest`; the Conversations API with `mistral-small-latest` still works for specs and prices), and the standard `PG*` vars read implicitly by `new Pool()` (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`). The `POSTGRES_*` vars in `.env` are unused leftovers.
- Local DB is the `postgres` Docker container (database `movifi_db`), reached by its container IP in `PGHOST`, because port 5432 is not published to the host. Port 5050 is pgAdmin's web UI, not Postgres. The IP can change when Docker restarts.
- Auth: `POST /auth/google` verifies a Google ID token (audience = `GOOGLE_CLIENT_ID`, which must be the web client of the Firebase project) and issues a 7-day JWT; other routes use the `auth` middleware (Bearer token -> `req.usuarioId`). Per-vehicle routes must check ownership with `vehiculoDeUsuario(id, usuarioId)`.
- Mistral AI (`api.mistral.ai/v1/conversations`) looks up vehicle specs via web search once per model (`buscarSpecsVehiculo`, cached in `especificaciones_vehiculo`); `/vehiculos/:id/chat` uses chat completions with read-only tools and no conversation memory. Tool arguments come from the model, so they are validated (`fechaValida`); the system prompt carries today's date and the currency (soles).
- Fuel: each vehicle stores `combustible_grado`, a reference `precio_galon` and an optional `rendimiento_manual` (overrides the AI's km/gal estimate). `precioReferencia(grado)` asks Mistral for the average S/ per gallon and caches it in `precios_combustible` for 7 days; users correct it, they do not enter it per fill-up. Fuel is bought by amount in Peru (S/ 30, 50, 100), so there is no full-tank / real-mileage calculation. `costo_por_km` is real (gastos since registration / km driven since `km_inicial`) and `null` until 50+ km are driven; `combustible.costo_por_km` = precio / rendimiento is the fallback.
- "Libre para gustos" (`calcularLibre`): disponible (presupuesto - gastado) minus combustible still to buy this month (`combustible_mensual` declared by the user, else the average of the previous 3 full months, else 0), minus maintenances due by month-end (priced at their last payment), minus a 10% imprevistos cushion (`IMPREVISTOS_PCT`). `evaluarCompra` turns it into a deterministic verdict (si / justo / no); it backs both `POST /vehiculos/:id/me-alcanza` and the chat tool `evaluar_compra`, so purchase answers never depend on the model doing arithmetic.
- Fuel gauge: the tank is 10 bars (`BARRAS`); one bar = capacity/10 gallons (`capacidad_manual` overrides the AI's `capacidad_tanque_galones`). `PUT /vehiculos/:id/nivel-combustible` (`registrarNivel`) stores the level; when it drops it logs the tramo (gallons, estimated cost and, if km are known, real km/gal) in `lecturas_combustible`, and when it rises with `monto` it also inserts a Combustible gasto. Real mileage is only kept if 1+ bar was used and the result is within 5-150 km/gal; `resumenCombustible.rendimiento_real` averages the last 5 tramos and the UI offers it (never applies it silently). `calcularCarga` and `estimarViaje` (also chat tools) are pure arithmetic over price/mileage/capacity.
- Dates: `DATE` columns are parsed as plain `AAAA-MM-DD` strings (`types.setTypeParser(1082, ...)`) and `sumarMeses` does calendar math without time zones (31 Aug + 6 months = 28 Feb), so nothing shifts by a day on a UTC server. The frontend reads them with `parseFecha` (local date) for the same reason.
- Estimated odometer (`odometroEstimado`): `km_actual` (what the user registered) + the sum of `lecturas_combustible.km_estimados` since `km_actualizado` (the last time a real odometer was set via PATCH, a gauge reading with higher km, or a gasto with higher km). Fuel consumed between readings is `previous level + bought bars - new level`; with real km it feeds the real mileage, without them it becomes estimated km (gallons x mileage). `registrarNivel` accepts `nivel_antes` (what the gauge showed right before refuelling) so consumption before a fill-up is not lost. Km-based maintenance alerts use the estimated odometer. Use `clock_timestamp()`, not `now()`, for these timestamps (`now()` is constant inside a transaction).
- Recorrido parcial (informational trip meter): `odometro.parcial.km` = estimated odometer - `parcial_km_base`, reset by `POST /vehiculos/:id/recorrido/reiniciar`. It is independent of maintenance alerts and of the estimate resetting when a real odometer is entered (a real value just corrects it).
- Gastos cannot be future-dated (POST rejects them) and maintenance tracking ignores any future-dated service. `notas` are free notes per vehicle (CRUD endpoints, also readable by the chat via `obtener_notas`).
- `GET /vehiculos/:id/copiloto`: `hechosCopiloto` builds the day's alerts with fixed rules; the model only phrases them (cached per vehicle/day/hash in `consejos_diarios`), falling back to the rule text if the AI call fails or its text is rejected (`redactarConsejo` discards any number that is not in the facts and any mention of fines/laws; the model did invent a fine amount once).
- Maintenance tracking is always derived from history (`recalcularMantenimiento`): the latest service among the `gastos` with that `tipo_mantenimiento_id` (each stores the `km` at service time) and the optional baseline the user gave when starting to follow it (`base_fecha`/`base_km`, via `seguirMantenimiento`). It runs after every gasto insert AND delete, so tracking can never go stale; a service with unknown km alerts by date only. The odometer only moves forward.

## Frontend (`movifi-frontend/`)

Angular 22 standalone components (no NgModules, signals, new control flow), SCSS, Vitest + jsdom. Install with `npm` (the lockfile is npm's). Run from `movifi-frontend/`:
- `npm start` - dev server on :4200 (talks to the backend at `API_URL` in `src/app/config.ts`, default `http://localhost:3000`)
- `npm run build` - production build
- `npm test` - unit tests; single file: `npx ng test --include=src/app/app.spec.ts`
- Formatting: Prettier (`printWidth` 100, single quotes).

Two screens, both lazy-loaded in `app.routes.ts`: `login/` (`/`) and `finanzas/` (`/finanzas`, behind `authGuard`; `invitadoGuard` bounces logged-in users off the login).
- Login goes through Firebase Auth (`signInWithPopup`) only to obtain a Google `id_token`, which `AuthService` posts to `/auth/google`. The backend JWT is stored in `localStorage` and attached by `authInterceptor`, which sends the user back to login on any 401. The Firebase web config in `config.ts` is public by design.
- `finanzas/` state lives in `FinanzasStore` (provided on the `Finanzas` component, not root): vehicle, dashboard, gastos, mantenimientos, plus derived signals (budget, category colors, maintenance status, health score). Child components (`tarjeta-notas`, `tanque-combustible` (the 10-bar gauge beside the car, inside `hero-vehiculo`), `viaje-form`, `tarjeta-copiloto`, `tarjeta-libre`, `hero-vehiculo`, `tarjeta-presupuesto`, `grafico-gastos`, `panel-mantenimientos`, `lista-gastos`, `gasto-form`, `chat-widget`, `vehiculo-form`) inject it instead of using inputs. A user with no vehicle sees `vehiculo-form` first.
- `shared/` holds the SVG `Medidor` (gauge) and `AutoDeportivo` components used by both screens, and the `soles` / `fechaCorta` pipes. Global tokens and utility classes (`.tarjeta`, `.btn`, `.campo`) are in `src/styles.scss`.
- Postgres `NUMERIC` columns reach the frontend as strings; convert with `Number()` (the store does this).
